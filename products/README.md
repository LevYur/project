# Products Service

Сервис **Products** отвечает за хранение и предоставление информации о товарах интернет-магазина.

Он предоставляет HTTP и gRPC API для получения информации о товарах, хранит данные в PostgreSQL, использует Redis для ускорения чтения и публикует события в Kafka при изменении данных, чтобы остальные сервисы могли своевременно обновить свой кэш.

---

# Назначение сервиса

Сервис отвечает за следующие задачи:

* хранение каталога товаров;
* получение информации о товаре;
* получение списка товаров;
* создание и обновление товаров;
* удаление товаров;
* кэширование наиболее часто запрашиваемых данных;
* публикация событий об изменении товаров;
* предоставление данных другим сервисам по gRPC.

---

# Архитектура

Сервис построен по слоистой архитектуре.

```text
HTTP / gRPC
      │
      ▼
  Handlers
      │
      ▼
   Service
      │
      ▼
 Repository
      │
 ┌────┴──────────┐
 ▼               ▼
Redis       PostgreSQL
      │
      ▼
    Kafka
```

Внешние клиенты используют HTTP API.

Внутренние сервисы получают информацию о товарах через gRPC.

При изменении данных сервис публикует события в Kafka.

---

# Основные компоненты

## HTTP API

Предоставляет REST API для работы с каталогом товаров.

Основные операции:

* получение товара;
* получение списка товаров;
* создание товара;
* обновление товара;
* удаление товара.

---

## gRPC API

Используется внутренними сервисами.

Основная задача — быстро предоставить актуальную информацию о товаре без обращения по HTTP.

Например, Cart Service получает:

* название;
* цену;
* изображение;
* другую информацию о товаре.

---

## Service Layer

Содержит основную бизнес-логику.

Основные задачи:

* обработка запросов;
* работа с каталогом товаров;
* управление кэшем;
* публикация событий в Kafka.

---

## Repository Layer

Отвечает за взаимодействие с хранилищами данных.

Используются:

* PostgreSQL — постоянное хранение товаров;
* Redis — кэширование популярных запросов.

---

## Kafka Producer

После изменения товара сервис публикует событие в Kafka.

Другие сервисы (например Cart Service) используют эти события для инвалидации собственного кэша и получения актуальной информации о товарах.

---

# Хранение данных

## PostgreSQL

Основное постоянное хранилище.

Для каждого товара сохраняются:

* идентификатор;
* название;
* описание;
* цена;
* изображение;
* служебная информация.

---

## Redis

Используется для:

* кэширования карточек товаров;
* ускорения повторных запросов;
* снижения нагрузки на PostgreSQL.

Кэш работает по стратегии **Cache-Aside**.

---

# Взаимодействие с другими сервисами

Products Service является владельцем данных о товарах.

Другие сервисы не хранят полную информацию о товарах, а получают её по gRPC.

После изменения товара сервис публикует событие в Kafka, позволяя другим сервисам своевременно обновить свои данные.

---

# Мониторинг

Сервис поддерживает централизованное логирование и сбор метрик.

Используются:

* Prometheus;
* Zap.

Собираются метрики времени обработки запросов, ошибок и обращений к внешним зависимостям.

# Основные архитектурные решения

* сервис является единственным владельцем данных о товарах;
* Redis используется для ускорения чтения;
* PostgreSQL используется как основное постоянное хранилище;
* внутреннее взаимодействие между сервисами выполняется через gRPC;
* Kafka используется для публикации событий об изменении товаров;
* сервис построен по слоистой архитектуре с разделением транспортного, бизнес- и слоя доступа к данным.
