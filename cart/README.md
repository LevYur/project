# Cart Service

Сервис **Cart** отвечает за управление корзинами пользователей в системе интернет-магазина.

Он предоставляет gRPC API для работы с корзиной, хранит её состояние в PostgreSQL, использует Redis для ускорения чтения данных и взаимодействует с сервисом **Products** для получения актуальной информации о товарах.

Кроме того, сервис подписывается на события Kafka для инвалидации устаревших данных о товарах в кэше.

---

# Назначение сервиса

Сервис отвечает за следующие задачи:

* хранение корзин пользователей;
* добавление и удаление товаров;
* получение текущего состояния корзины;
* очистка корзины;
* расчёт итоговой стоимости заказа;
* получение актуальной информации о товарах из Product Service;
* кэширование корзин и информации о товарах;
* инвалидация устаревшего кэша при изменении товаров.

---

# Архитектура

Сервис построен по классической слоистой архитектуре.

```text
gRPC Server
      │
      ▼
  Handlers
      │
      ▼
   Service
      │
      ▼
 Repository
      │
 ┌────┴──────────┐
 ▼               ▼
Redis       PostgreSQL
```

Для получения информации о товарах используется gRPC-клиент Product Service.

Для асинхронной инвалидации кэша используется Kafka.

---

# Основные компоненты

## gRPC Server

Предоставляет API для взаимодействия с другими сервисами системы.

Основные операции:

* добавление товара в корзину;
* удаление товара;
* получение содержимого корзины;
* очистка корзины.

---

## Service Layer

Содержит основную бизнес-логику сервиса.

Основные задачи:

* обработка запросов;
* управление состоянием корзины;
* расчёт итоговой стоимости;
* получение информации о товарах;
* синхронизация Redis и PostgreSQL.

---

## Repository Layer

Отвечает за работу с хранилищами данных.

Используются:

* PostgreSQL — постоянное хранение корзин;
* Redis — быстрое получение данных.

---

## Product Client

В корзине хранится только минимальный набор информации:

* идентификатор товара;
* количество.

Остальные данные (название, цена, изображение и т.д.) запрашиваются у Product Service по gRPC.

Такой подход позволяет избежать дублирования данных и всегда получать актуальную информацию о товарах.

---

## Kafka Consumer

Сервис подписывается на события Product Service.

При изменении информации о товаре происходит инвалидация соответствующего кэша.

При следующем обращении актуальные данные снова загружаются из Product Service.

---

# Хранение данных

## PostgreSQL

Используется как основное постоянное хранилище.

Для каждой корзины сохраняются:

* идентификатор пользователя;
* список товаров;
* количество каждого товара;
* служебная информация.

Данные о самих товарах не дублируются.

---

## Redis

Используется для:

* кэширования корзин;
* хранения информации о товарах;
* снижения нагрузки на PostgreSQL.

Кэш работает по стратегии **Cache-Aside**.

---

# Мониторинг

Для мониторинга используются метрики Prometheus.

Сервис собирает информацию о:

* времени обработки запросов;
* времени работы с PostgreSQL;
* времени работы с Redis;
* количестве запросов;
* ошибках работы с БД;
* ошибках Redis.

Для логирования используется библиотека **Zap**.

# Основные архитектурные решения

* сервис построен по слоистой архитектуре;
* Redis используется для ускорения операций чтения;
* PostgreSQL является основным постоянным хранилищем;
* информация о товарах не хранится в корзине, а запрашивается у Product Service по gRPC;
* Kafka используется для инвалидации устаревших данных в кэше;
* Prometheus и Zap обеспечивают мониторинг и логирование сервиса.
