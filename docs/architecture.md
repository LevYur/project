# Архитектура проекта

Проект представляет собой микросервисную систему интернет-магазина.

Основная цель архитектуры — разделить ответственность между сервисами, вынести бизнес-логику из единого приложения и показать разные способы взаимодействия сервисов: HTTP, gRPC, Redis, PostgreSQL и брокеры сообщений.

# Основные сервисы

## Gateway Service

Gateway является единой точкой входа в систему.

Он принимает HTTP-запросы от клиентов, применяет middleware, проверяет JWT-токены и маршрутизирует запросы во внутренние сервисы.

Gateway не содержит основной бизнес-логики. Его задача — транспортный слой, безопасность, маршрутизация и наблюдаемость.

---

## Auth Service

Auth отвечает за регистрацию и авторизацию пользователей.

Сервис хранит пользователей в PostgreSQL, выпускает JWT-токены и публикует событие после регистрации пользователя.

В текущей версии Auth частично закрывает обязанности Users Service.

---

## Products Service

Products является владельцем данных о товарах.

Сервис хранит каталог товаров в PostgreSQL, кэширует часто запрашиваемые данные в Redis и предоставляет HTTP/gRPC API для получения информации о товарах.

При изменении товара сервис публикует событие в Kafka.

---

## Cart Service

Cart отвечает за управление корзинами пользователей.

В корзине хранится минимальный набор данных: идентификатор товара и количество.

Актуальная информация о товаре запрашивается у Products Service по gRPC.

Cart использует Redis для ускорения чтения и PostgreSQL для постоянного хранения корзин.

---

## Users Service (planned)

Users Service планировался как отдельный сервис пользовательских профилей.

Он должен был получать событие о регистрации пользователя из брокера сообщений и хранить профиль пользователя в собственной базе данных.

В текущей версии сервис описан как запланированный компонент.

---

# Виды взаимодействия

В проекте используются несколько типов взаимодействия между компонентами.

---

# HTTP

HTTP используется для взаимодействия клиента с системой.

Клиент не обращается к внутренним сервисам напрямую.

```text
Client
   │
   │ HTTP
   ▼
Gateway Service
```

Такой подход позволяет централизованно реализовать:

* маршрутизацию;
* авторизацию;
* rate limiting;
* логирование;
* сбор метрик;
* обработку ошибок.

---

# gRPC

gRPC используется для синхронного взаимодействия между внутренними сервисами.

```text
Gateway Service
      │
      ├──► Auth Service
      ├──► Products Service
      └──► Cart Service

Cart Service
      │
      └──► Products Service
```

gRPC выбран для внутренних вызовов, потому что он хорошо подходит для service-to-service взаимодействия, имеет строгие контракты через `.proto`-файлы и позволяет явно описывать API между сервисами.

---

# Kafka

Kafka используется для асинхронного взаимодействия между Products Service и Cart Service.

Основной сценарий — инвалидация кэша при изменении товара.

```text
Products Service
        │
        │ product updated event
        ▼
      Kafka
        │
        ▼
 Cart Service
```

Когда информация о товаре изменяется, Products Service публикует событие.

Cart Service получает это событие и инвалидирует устаревшие данные в Redis.

---

# RabbitMQ

RabbitMQ используется для событий, связанных с пользователями.

```text
Auth Service
      │
      │ user registered event
      ▼
   RabbitMQ
      │
      ▼
Users Service (planned)
```

После регистрации пользователя Auth Service публикует событие.

В целевой архитектуре Users Service должен был получать это событие и создавать пользовательский профиль.

---

# Redis

Redis используется как быстрый кэш для операций чтения.

```text
Service
   │
   ├──► Redis
   │       │
   │       └── cache hit
   │
   └──► PostgreSQL
           │
           └── cache miss
```

Redis применяется в следующих сервисах:

* Products Service — кэширование информации о товарах;
* Cart Service — кэширование корзин и информации о товарах.

Основная стратегия работы с кэшем — **Cache-Aside**.

---

# PostgreSQL

PostgreSQL используется как основное постоянное хранилище данных.

Каждый сервис работает со своей областью данных:

* Auth Service — пользователи и учетные данные;
* Products Service — товары;
* Cart Service — корзины.

Такой подход соответствует принципу database-per-service, при котором сервис владеет собственными данными и не обращается напрямую к таблицам другого сервиса.

---

# Observability

Для наблюдаемости используются:

* Prometheus;
* Grafana;
* Loki;
* Promtail;
* Zap.

```text
Services
   │
   ├──► Prometheus ───► Grafana
   │
   └──► Logs ─────────► Promtail ───► Loki ───► Grafana
```

Сервисы собирают метрики и структурированные логи.

Prometheus используется для сбора метрик.

Grafana используется для визуализации.

Loki и Promtail используются для централизованного сбора и просмотра логов.

---

# Конфигурация и запуск

Проект запускается через Docker Compose.

В корне проекта находятся:

```text
compose.yaml
compose.infra.yaml
```

`compose.yaml` описывает прикладные сервисы.

`compose.infra.yaml` используется для инфраструктурных компонентов:

* PostgreSQL;
* Redis;
* Kafka;
* RabbitMQ;
* Prometheus;
* Grafana;
* Loki;
* Promtail.

---

# Работа с protobuf

Контракты gRPC вынесены в отдельный репозиторий:

```text
project-protos
```

Это позволяет разделить код сервисов и описание межсервисных контрактов.

Основные сервисы используют сгенерированный Go-код из `.proto`-файлов для gRPC-взаимодействия.

---

# Основные архитектурные решения

* используется микросервисная архитектура;
* Gateway является единой точкой входа;
* внутреннее взаимодействие выполняется через gRPC;
* асинхронные события передаются через Kafka и RabbitMQ;
* каждый сервис отвечает за свою область данных;
* PostgreSQL используется как постоянное хранилище;
* Redis используется как кэш;
* Prometheus, Grafana, Loki и Promtail используются для наблюдаемости;
* protobuf-контракты вынесены в отдельный репозиторий;
* Users Service описан как запланированный компонент, но не входит в текущую реализацию.
